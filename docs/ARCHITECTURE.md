# Как всё устроено

## Модель данных

Две основные таблицы: дерево разделов и блоки внутри карточек.

```
nodes (дерево)                         blocks (содержимое карточки)
├─ id                                  ├─ id
├─ parent_id ──┐  ссылка на себя       ├─ node_id ──> nodes.id
├─ title       │                       ├─ label      «ТПО», «Тироцит»
├─ subtitle    │                       ├─ color      red | green | gold
├─ kind        │  chapter/topic/       ├─ content    документ редактора (JSONB)
├─ icon        │  branch/card          ├─ content_text  плоский текст для поиска
├─ position    │  порядок у соседей    ├─ position
└─ search_vector  (генерируется)       └─ search_vector (генерируется)
```

### Почему дерево, а не четыре отдельные таблицы

В интерфейсе уровней четыре: глава → тема → ветка → карточка. Но хранятся они
одной таблицей со ссылкой `parent_id` на саму себя. Это даёт:

- добавление пятого уровня без миграций;
- один запрос вместо четырёх — всё дерево грузится разом;
- общий код перемещения, переименования и удаления.

Поле `kind` отвечает только за подписи и за то, какой экран рисовать.

### Почему блоки — отдельная таблица, а не одно большое поле

Ключевой сценарий: «нашёл дополнительную информацию — дополняю **именно ТПО**».
Отдельная строка на блок означает, что правка задевает ровно один блок, история
пишется поблочно, а поиск показывает, в каком именно блоке нашлось совпадение.

### Каскады и триггеры

- Удаление узла удаляет всех потомков и их блоки (`ON DELETE CASCADE`).
- `blocks_before_update_trg` перед каждой правкой кладёт прошлую версию блока
  в `block_revisions` (`op = 'update'`).
- `blocks_before_delete_trg` и `nodes_before_delete_trg` перед удалением кладут
  туда же последнюю версию (`op = 'delete'`) вместе с `node_id` и `path` —
  полным путём до карточки. У `block_revisions` нет внешнего ключа на `blocks`
  именно поэтому: иначе каскад уносил бы историю вместе с блоком. Удалённый
  раздел целиком восстанавливается из истории руками, через SQL.
- `blocks_bump_node_trg` обновляет `nodes.updated_at` — благодаря этому на
  главной работает список «Недавно дополнено». Перестановка блоков или записей
  стрелками меняет только `position` и дату не трогает (`touch_node` и
  `bump_node_from_block` это проверяют).
- `nodes_check_cycle_trg` не даёт положить раздел внутрь самого себя.

### Права (RLS)

| Таблица | Чтение | Запись |
|---|---|---|
| `nodes`, `blocks` | все | только редактор |
| `app_settings` | все | только редактор |
| `block_revisions` | редактор | редактор |
| `editors` | своя строка | только через SQL или `claim_editor()` |
| `editor_invite` | никто | никто |
| бакет `notes` | все | только редактор |

«Редактор» — это функция `is_editor()`: есть ли `auth.uid()` в таблице `editors`.
Она объявлена `security definer`, поэтому сама не упирается в RLS.

### Как аккаунт становится редактором

Читать может кто угодно, поэтому открытая регистрация сделала бы редактором
любого, кто нашёл адрес. Вместо этого при регистрации спрашивается код
приглашения — секретная фраза, которую владелец кладёт в `editor_invite` один
раз из SQL Editor.

Проверяет её `claim_editor(p_code)`: сверяет фразу и, если совпала, вставляет
`auth.uid()` в `editors`. Функция `security definer` — иначе она не смогла бы
писать в `editors`, у которой нет политики на вставку; звать её разрешено только
роли `authenticated`. У самой `editor_invite` включён RLS и **нет ни одной
политики**, так что фразу нельзя ни прочитать, ни изменить через API — её видит
только эта функция.

Фраза должна быть длинной: функция доступна любому вошедшему, и короткое слово
рано или поздно переберут. Когда приглашение отработало, код стирается
(`update editor_invite set code = null`), и функция перестаёт срабатывать вовсе.

Вход, регистрация и «забыли пароль» — на `/login` (`LoginPage`); после входа и
регистрации она ведёт на главную, а вошедшего перенаправляет туда же. Всё про
аккаунт — ввод кода, смена почты и пароля, выход со всех устройств — живёт в
профиле `/profile` (`ProfilePage`, значок аккаунта в шапке). Если проект Supabase требует
подтверждения почты, после `signUp` сессии ещё нет — тогда код вводится позже,
после входа, уже в профиле.

Смена пароля просит текущий: Supabase его сам не проверяет, поэтому
`changePassword` в `AuthContext` сначала делает `signInWithPassword` со старым.
Исключение — вход по ссылке восстановления: событие `PASSWORD_RECOVERY`
поднимает флаг `recovery`, и профиль просит только новый пароль. Ссылка из
письма ведёт на `/profile`, так что адрес сайта должен быть в Redirect URLs
Supabase (см. `docs/SETUP.md`). Смена почты — `updateUser({ email })`: Supabase
шлёт письма на оба адреса, до подтверждения новая видна в `user.new_email`.

### Поиск

Функция `search_all(q, lim)` объединяет два источника:

1. названия и подзаголовки узлов;
2. метки и текст блоков.

Оба используют русский словарь Postgres, плюс подстраховка через `ILIKE` для
частичных слов вроде «коагул» (служебные `%` и `_` из запроса экранируются).
Результат всегда содержит `id` карточки, которую нужно открыть, а если совпало
в блоке — его `label` и `color`. Фрагмент текста приходит с маркерами `[[…]]`,
которые фронтенд превращает в подсветку — так исключён любой риск подстановки
HTML.

Набор колонок у `search_all` менялся, поэтому в схеме она не `create or
replace`, а `drop function` + `create` — `create or replace` не умеет менять
тип результата.

### Утилита импорта

`text_to_doc(text)` превращает обычный текст в документ редактора: каждая
непустая строка становится абзацем. Пригодится, чтобы залить старые конспекты
одним `INSERT`.

### Почему дерево грузится целиком

Один запрос отдаёт все узлы без содержимого. Для базы в тысячи записей это
десятки килобайт, зато переходы между разделами мгновенные и не мигают. Тяжёлое
содержимое — блоки — грузится только для открытой карточки.

PostgREST отдаёт не больше 1000 строк за раз, поэтому `fetchTree` забирает
таблицу страницами (`fetchAllPages` в `api.ts`) — иначе дерево молча обрезалось
бы, а дети без родителей становились бы корнями.

### Почему чтение без TipTap

TipTap с ProseMirror — почти половина кода приложения (≈130 КБ gzip), а
читателю он не нужен. Поэтому `NoteView` рисует документ сам: `render.tsx`
превращает JSON в React-элементы с той же разметкой, которую выдаёт редактор
(`<p>`, `<h2>`, `<ul>`, `<img>`, `<span class="term">`…). Редактор
(`BlockEditor` → `NoteEditor` → TipTap) подгружается отдельным куском только по
кнопке «Редактировать» или «Добавить блок».

Отсюда правило: `render.tsx` и `tiptap-config.ts` должны уметь одно и то же.
Добавили расширение редактору — добавьте ветку в рендер. Незнакомый узел рендер
не роняет, а показывает его содержимое; на случай совсем испорченного документа
каждый блок обёрнут в `ErrorBoundary`.

Всё, что нужно документу без TipTap (`contentToText`, `extractTerms`,
`imageUrls`), живёт в `doc.ts`. Импортировать `editor.ts`, `tiptap-config.ts`
или `NoteEditor` откуда-то кроме `BlockEditor` нельзя — TipTap вернётся в
основной кусок.

### Запись: сессия, повторы, идемпотентность

На телефоне сеть «моргает», а токен Supabase живёт час и успевает истечь, пока
пишется длинный блок или приложение спит в фоне. Все записи в `api.ts` идут
через `write()`:

1. перед запросом `ensureSession()` проверяет срок токена и при необходимости
   обновляет его заранее;
2. ошибка сессии или RLS → обновить сессию и повторить; обрыв сети или 5xx →
   подождать и повторить (три попытки с нарастающей паузой); совсем без сети
   (`navigator.onLine === false`) — сразу сказать;
3. у новых строк id генерируется на клиенте, а вставка идёт через `upsert`:
   повтор после обрыва не создаст дубликата. Повторная загрузка картинки с тем
   же путём, которая отвечает «уже существует», тоже считается успехом;
4. наружу уходит `Error` с текстом по-русски (`describeError`) — его и
   показывают под кнопкой «Сохранить». Текст остаётся в редакторе и в черновике,
   можно просто нажать ещё раз.

После успешной записи `invalidateData(...)` просит service worker забыть
устаревшие ответы, иначе следующий заход показал бы прошлую версию.

Блок при этом сохраняется **в фоне**: `BlockEditor` по «Сохранить» отдаёт
`BlockList` локальную версию и функцию `commit`, редактор закрывается сразу, а
блок показывается в чтении с пометкой «Сохраняется…». У нового блока id
генерируется на клиенте заранее, поэтому он встаёт в список до ответа сервера.
Не записалось — под меткой появляется ошибка и кнопка «Открыть и повторить»;
черновик стирается только после успеха, а тихая перезагрузка списка
(`DATA_UPDATED`) не выбрасывает блоки, которые ещё пишутся или не записались.

### Черновики

Пока блок редактируется, его содержимое через секунду после каждой правки
откладывается в `localStorage` (`drafts.ts`, ключ по id блока или по карточке
для нового). Сохранили или нажали «Не сохранять» — черновик стирается. Если
приложение закрылось раньше, при следующем открытии редактора для того же блока
появится предложение восстановить.

### Фотографии

`uploadImage` перед отправкой уменьшает картинку в браузере (`image.ts`):
длинная сторона до 2048 px, JPEG 0.85, PNG остаётся PNG, только если в нём есть
прозрачность. Фото с телефона из 8 МБ превращается в 300–500 КБ — это и быстрая
загрузка с мобильной сети, и быстрые страницы у всех читателей. Размеры
записываются в атрибуты картинки, чтобы страница не прыгала, пока фото грузится.

### Размер текста

У текста конспекта своя настройка, отдельная от общего масштаба: размер
(`NOTE_SIZES`, 14–20px) и межстрочное (`NOTE_LEADINGS`: компактно / обычно /
свободно). По умолчанию 16px и компактно — «как в Telegram»: длинный конспект
так читается быстрее. Значения раздаются переменными `--note-size` и
`--note-leading`, их читает `.prose-note` (`index.css`, блок «Редактор и
чтение»); в редакторе на 1px мельче — над клавиатурой помещается больше строк.
Настройка личная, хранится в `localStorage`.

Значения размеров в разметке заданы в пикселях, поэтому обычный приём с
`font-size` на `:root` не сработал бы. Вместо этого масштаб раздаётся
переменной `--app-zoom`, а свойство `zoom` вешается на содержимое: дерево,
`main` и панели модальных окон. Шапка, мобильная шторка и полоса состояния
берут отдельную `--shell-zoom`: на широких экранах она равна `--app-zoom`, а
уже 640px — единице, иначе при 130–150 % строка с иконками не помещалась,
страница становилась шире экрана и телефон отдалял её целиком.

Из-за этого сами модальные окна и просмотр фотографии рендерятся порталом в
`body` — иначе подложка внутри масштабированного блока считала бы размеры от
него, а не от экрана, и окно съезжало бы. Высоты, завязанные на экран
(`92vh`, `60vh`, высота бокового дерева), делятся на `var(--app-zoom)`.

### Офлайн и быстрый запуск

`public/sw.js` — service worker без сборщиков и зависимостей. Три кэша:
оболочка (`/assets/*` с хэшами в именах), данные (`GET /rest/v1/*`) и файлы
(картинки хранилища, шрифты, скрипт Telegram). Записи и авторизация в кэш не
попадают никогда.

Правила:

- **Данные** — «сохранённое сразу, свежее в фоне». Страница открывается
  мгновенно из кэша; когда приходит ответ сервера и он отличается, worker шлёт
  страницам `DATA_UPDATED` с адресом, и подписчики (`onDataUpdated` в
  `sw-client.ts`: дерево, блоки, настройки, права редактора) тихо перечитывают.
  Права попали в этот список не сразу: выдать их можно не из этого браузера —
  кодом приглашения с другого устройства или строкой в `editors` через SQL, —
  а ответ «этот аккаунт не редактор» к тому моменту уже лежит в кэше. Без
  подписки приложение показывало бы читательский вид до второй перезагрузки.
  Отсюда правило: **любое кэшируемое чтение нуждается в подписке**. После записи
  приложение шлёт `INVALIDATE`, и устаревшие ответы забываются — своя правка
  никогда не покажется старой версией.
  Копию сохранённого ответа для сравнения worker снимает **до** того, как отдаёт
  его странице: после `respondWith` тело считается использованным, и `clone()`
  бросает `TypeError`. Ошибка попадала в пустой `catch`, и вместе со сравнением
  отменялись запись свежего ответа и сигнал. Сохранённое дерево не обновлялось
  никогда: чужие правки не появлялись ни после перезагрузки, помогала только
  очистка данных сайта. Чинено в `VERSION = v4`.
- **Оболочка** — `/assets/*` сначала из кэша (имена с хэшем). Переход по адресу
  ждёт сеть не дольше трёх секунд, если есть сохранённый `index.html`; дальше
  маршрут разбирает само приложение, а свежая оболочка дотягивается в фоне.
- **Файлы** — сначала кэш. Чтобы ответы на `<img>` и `<link rel=stylesheet>`
  вообще попадали в кэш, у них стоит `crossorigin`: без него браузер отдаёт
  «непрозрачный» ответ со статусом 0, и worker не может проверить, что он
  успешный. Supabase Storage, Google Fonts и telegram.org отдают
  `Access-Control-Allow-Origin: *`, так что это безопасно.

Регистрируется только в собранной версии: в разработке кэш мешал бы правкам.
Проверять — на `npm run build` и любом статическом сервере поверх `dist`.
Изменили `sw.js` — поднимите `VERSION`.

Кнопка «Скачать» в настройках проходит по всем карточкам и их фотографиям,
чтобы в кэше оказалось и то, что ещё ни разу не открывали. Поиск по тексту
офлайн не работает: он живёт в базе. Поиск по названиям — работает, дерево
целиком лежит в памяти.

### Когда данные перечитываются

Дерево и блоки читаются при запуске и по `DATA_UPDATED`. Этого мало: телефон
держит приложение открытым сутками, и дополненный с другого устройства конспект
до перезагрузки не появлялся. `lib/visibility.ts` — один общий слушатель
возврата во вкладку: `visibilitychange` и вдобавок `pageshow`, потому что
возврат кнопкой «назад» поднимает страницу из bfcache, не меняя видимости.

Перечитывают `TreeContext` и `BlockList`, не чаще раза в 20 секунд (мелькание
между вкладками — не новый заход) и с отсчётом от загрузки страницы. Идёт это
через service worker, то есть сначала из кэша: экран не мигает, свежее
подставляется тем же путём «сохранённое сразу, свежее в фоне». Блоки при
открытом редакторе не перечитываются — отошли посмотреть учебник, вернулись, а
текст подменился бы под руками.

### Загрузка

В `index.html`: `preconnect` к Supabase (адрес подставляет Vite из
`VITE_SUPABASE_URL`), шрифты — переменные начертания одним файлом на семейство
и без блокировки отрисовки (`media="print" onload`), скрипт Telegram с
`crossorigin`, чтобы worker его сохранил. Основной кусок JS — около 160 КБ gzip,
редактор — ещё 130 КБ по требованию.

### Темы

Каждая тема — набор CSS-переменных на `[data-theme="…"]` в `src/index.css`.
Компоненты нигде не хардкодят цвет, только `var(--fg)`, `var(--accent)` и так
далее. Поэтому новая тема добавляется правкой одного файла и одного массива
`THEMES`.

Тема выставляется inline-скриптом в `index.html` до первой отрисовки — иначе на
загрузке моргал бы белый экран.

### Что осталось недоделанным

Сознательные упрощения — не забытые дела, а места, где решили остановиться.
Если что-то из этого начнёт мешать, вот куда смотреть.

| Что | Как сейчас | Куда смотреть |
|---|---|---|
| Обновление офлайн-копии | Открытые страницы обновляются сами — при запуске и при возврате во вкладку, — но карточка, добавленная после «Скачать», в кэш не попадёт, пока её не откроют | `prefetchForOffline` в `lib/offline.ts` — можно звать тихо при запуске |
| Память сворачивания | Один общий выбор на все карточки (`lichnoe-info-blocks-collapsed`), состояние конкретной карточки не хранится | `BlockList.tsx`, константа `COLLAPSE_PREF` |
| Поиск офлайн | По названиям работает (дерево в памяти), по тексту блоков — нет: `search_all` вызывается как RPC, то есть POST, а POST не кэшируется | `sw.js`, `SearchPalette.tsx` |
| История в интерфейсе | `block_revisions` пишется при каждой правке и удалении, но показывать и откатывать версии приложение не умеет — только руками через SQL | `supabase/schema.sql`, триггеры `*_before_*` |
| Старые файлы в хранилище | Картинка, убранная из текста, остаётся в бакете `notes`; чистки нет | `api.ts`, `uploadImage` |
| Уход со страницы при правке | Вопрос «есть несохранённое» задаётся при переходе к другому блоку и по «Отмена»; переход по ссылке его не задаёт — выручает черновик | `BlockList.tsx`, `drafts.ts` |
